# 设计与踩坑记录

面向想改这个脚本的人。README 讲怎么用，这里讲**为什么这么判**，以及每条规则背后是哪次误伤换来的。改判定逻辑前先读这一篇。

## 1. 为什么不能靠调大 `stream_max_retries` 硬扛

Codex 的流式重连是固定指数退避，约 `0.2s × 2^(n-1)`，配置里只有次数、没有间隔可调：

| 第 n 次 | 这次要等 | 累计 |
|---:|---:|---:|
| 1 | 0.2s | 0.2s |
| 5 | 3.2s | 6s |
| 8 | 26s | 51s |
| 10 | 1.7min | **3.4min** |
| 12 | 6.8min | 14min |
| 15 | 55min | 1.8h |
| 20 | 21h | ~43h |

把次数从 10 调到 20 没有任何意义：前十次之后，单次等待就是几小时，比上游抽风还久，turn 一直挂在那儿空等。真正有用的是**在退避还短的时候把预算归零**——打断一次，重试计数回到 0，下一轮又是从 0.2s 开始。这就是本脚本存在的全部理由。

## 2. 界面读取的现实约束（都是实测）

| 事实 | 后果 |
|---|---|
| 重试次数是滚动数字动画，`textContent` 读出来是 `0123456789` | 真值在 `span[aria-label]` / `aria-valuenow` 上。直接正则匹配文本**永远匹配不到，而且不报错** |
| 历史重试行永久留在 transcript 里，次数冻结在 7–9 | 「最后一条重试行」既可能是正在进行的，也可能是上一轮残留。只靠它判断必然误触发 |
| 虚拟滚动会克隆节点 | 「换了一个 DOM 节点」不等于「新发生了重试」，克隆出来的高次数行要按残留处理 |
| 输入框 / 发送 / 停止 / 继续 是**同一个** composer 按钮 | 只能靠 `aria-label` 区分状态；而且不能全局扫 `button`，顶部工具栏有带同样 class 片段的按钮，必须以输入框为锚点向上限定作用域 |
| 界面可能被汉化，也可能英文 | 中英文文案都要认（见 `CONFIG.platform`） |
| 窗口最小化后 `getBoundingClientRect()` 常塌成 0×0 | 按几何判断「可见」会让所有按钮变成不可点，救援整条链哑掉。可见性判断必须先问「布局是否可用」，布局塌了只要求节点还挂在文档里 |

## 3. 状态机

```text
每拍（pollMs 轮询 + 后台 Worker 补拍 + 看门狗外部 kick）
  │
  ├─ 按钮 = 停止（turn 在跑）
  │    ├─ 重试行「跳号」（8/10 → 9/10）＝ 上一发失败已证实
  │    │     └─ 且失败的那一发 ≥ 本轮随机临界 T∈{7,8,9}
  │    │           └─ 进入验收窗 3~4s ─┬─ 出正文 / 重连行消失 / 按钮离开停止 / 出现限流 → 撤销
  │    │                              └─ 仍静默仍在重连 → 落稳 0.2~0.6s → 点停止 → 等 2.5~7s → 点「继续」
  │    └─ 次数停住不动 → 什么都不做（可能是刚接上在思考）
  │
  └─ 按钮 = 发送（turn 已停）
       ├─ 本 turn 跑起来过 + 新出现的错误框 + 连续存在 fatalConfirmMs → 死会话迁移
       ├─ 本轮重试打满且没产出 → 同会话发 continueText
       ├─ 有产出后正常收尾 → 脱离接管，排自托管读秒
       └─ 历史残留错误框 → 忽略

按钮 = 未知态（例如「排队」）→ 不点、不改状态机
```

## 4. 每条判定各自的由来

### 4.1 「活跃重试会话」——防止打断长思考

早期版本是「看到高次数重试行 + 界面静默 → 判定正在重试 → 打断」。错在：模型长时间思考时界面也是静默的，而 transcript 里那条冻结的 `8/10` 是上一轮留下的。结果正常思考被砍断。

现在要求**本 turn 内次数真的爬升过**（或出现从 1/2 起步的新行）才算活跃重试；并且启动时、新 turn 开始时、脚本动过手后、内容一旦产出，现存重试行全部降级为残留。次数停止爬升超过 `sessionIdleMs` 后即使还显示 8/10 也不动手。

### 4.2 跳号 + 验收窗——「万一这一发成功了呢」

`8/10 → 9/10` 只能证明**第 8 次失败**，不能证明第 9 次也会失败。看到跳号就立刻点停止，就会砍在「刚好连上、正在出首字」的那一发上。

所以跳号之后不立刻动手，先给一个 3–4s 的验收窗，让这一发有机会证明自己：出正文、重连行消失、按钮离开停止态、或者冒出限流，任一为真就撤销本次打断。窗口结束仍是「重连中且无正文」才打断——再拖就逼近 10/10 了。

### 4.3 限流要单独一条路

`rate limit exceeded … token rate limit` 和通道满是两回事：

| | 通道满 / 流断开 | token rate limit |
|---|---|---|
| 打断 + 继续 | 有效，重置重试预算 | **有害**，等于在限流上再加一次请求 |
| 正确动作 | 跳号证实失败后打断续跑 | 不做预防性打断，等它停下再发一句「继续」 |

限流文案可能在验收窗中途才刷出来，所以它是**一票否决**：窗内出现就撤销，`rescue()` 动手前还要再查一次。

**停下之后要立刻续跑，不能排自托管读秒。** 读秒是 30–300s 的随机间隔，限流场景下这段时间整条会话干等着。但「界面上看得到限流文案」不能当证据 —— 报错框会永久留在 transcript 里，那样点开任何一条历史限流会话都会被当成故障、一进来就发「继续」。所以证据换成三条同时成立：

1. **本轮新弹出一个报错框**。每拍顺手数限流文案有几份（和长度计算共用同一次遍历，不额外扫 DOM），比基准多才算新撞。基准在启动、turn 开始、切换会话时按当前 DOM 重定，虚拟滚动摘掉旧框时基准跟着下调（否则永远等不到「变多」）。
2. **撞框之后没有任何实质产出** —— 撞框后又跑了正文说明那一发连上了，是收尸现场的反例。
3. **本轮真的跑过**（见过停止钮）。光凭 1 会被滚动重新挂载的旧框骗到，而点开旧会话时按钮一直是发送态、这条不成立。

三条判据和「打满」那条走的是同一套结构：证据只在运行期产生、动手即消费、`maxRounds` 熔断。

### 4.4 死会话迁移（400 / 413 / 422）

重试是「流断了，请求本身没问题」，原地继续有效；而 400 是「请求被拒」，同一个会话再打同一个包必然还是 400，只能开新对话把任务接过去。

代价是它会**开新聊天**，误伤成本极高，因此叠了三道闸：

1. **会话切换复位** —— thread id 一变，`sawRunningTurn / engaged / turnThreadId` 全部清零，新会话里已有的错误框统统登记为残留；
2. **未跑过不迁** —— 本 turn 没见过停止按钮，一律当残留（否则「点开一条历史上带 400 的旧会话」就会被自动迁移）；
3. **延迟确认** —— 连续看到同一个请求标识满 `fatalConfirmMs`（默认 8s），期间没打字、没切会话，才允许动手。确认期内状态条显示「待确认」。

迁移文案默认是 `读取{threadId}，继续`：不摘简报、不带 transcript（否则新会话可能又超限），让新会话自己去读旧对话。

thread id 的取值优先级（这条修过两次，别乱改）：`/state` 面板的「会话/对话串」→ 侧栏选中行的 `local:01a0…` → React fiber 里的 `threadId` → 主对话区文本兜底。关键坑：`local:client-new-thread:UUID` 里那个 UUID **不是** thread id；而 `localStorage.codexThreadScroll` 取 `at` 最大会命中**别的**最近会话。turn 还在跑时要先打快照，否则切到新聊天后就读不到原 id 了。

### 4.5 耗尽续跑为什么不能挂在「活跃重试行」上

最初的条件是：按钮回到「发送」时，如果 `activeRetryEl` 还是那条行、且 `n >= max`、且没吐正文，就发「继续」。这个条件**永远等不到**，两个原因叠在一起：

1. **打满就是终态。** 10/10 之后次数不可能再爬升，而 `sessionIdleMs`（默认 30s）的空闲超时正是拿"次数还在不在爬"判断会话存活的 —— 于是耗尽后不到半分钟，会话就被判成残留、`activeRetryEl` 清空。而 Codex 从打出 10/10 到真正放弃、按钮回「发送」，实测要两分钟。等得到吗，等不到。
2. **报错文案被算成模型产出。** `threadLen` 是对话区文本长度，用来判断"有没有在输出"。一条 rate limit 报错框约 170 字，界面上同一段文案还会出现两份（错误框里一份、会话条目里一份），实测三条合计 324 字、占当时对话区 11.6% —— 远超 `growthEpsilon=40`。所以报错一弹，脚本看到的是「这一发成功了，开始出字」，当场撤销判定。

改法两条，缺一不可：

- **错误文案不计入产出。** `threadLen` 里扣掉命中限流/会话已死/high demand 文案的叶节点。前两种扣的时候**不做容器校验**（和 400 迁移相反：那边认错要付乱点界面的代价，宁可漏；这边漏扣只会让"没产出"更容易成立）；high demand 是唯一的例外，必须在 `fatalContainers` 里才算 —— 那句 "We’re currently experiencing high demand…" 本身是一句通顺的英文，模型正文里引用它完全可能，误扣就把真产出看没了。也**不能缓存**——报错出现的那一拍必须同时扣掉，缓存过期会让长度先跳一百多字再落回去，而那一跳足够把证据误清掉。
- **「打满」记成 turn 级证据。** 在 stop 态看到 `n >= max` 且这条行确实是当前活跃行时，把 `{el, at, len}` 存进 `state.turnExhausted`，它不受 `endRetrySession` 影响，只在新 turn 开始、切换会话、或打满之后真的开始出字时清掉。发送态的耗尽判定改成读这条证据。

证据只在运行期产生，所以「打开一条历史上带 10/10 的旧会话」不会触发续跑 —— 那是残留，不是本轮打满。

### 4.6 0.15.0：high demand 单独一类，先修「它把打断吃掉」

`We’re currently experiencing high demand, which may cause temporary errors.` 是通道池满载，按 4.3 的表格它属于「打断有效」那一列，本来就该走 7~9 随机临界。但脚本从来认不到它：`platform` 里三条正则（`retryText` / `rateLimitText` / `fatalText`）一句都不命中，于是那 75 个字符照 4.5 的老路被算成模型产出。真实会话日志（压缩时间轴前的原样）：

```
[22:24:33] 活跃重试 9/10（次数爬升）
[22:25:00] 重试会话结束（已产出内容，重试应已成功）   ← 该在 9 打断，被这句取消
[22:25:35] 第 10/10 打满：记下耗尽证据，等 turn 结束再决定续跑
[22:25:35] 第 9 次失败已证实（n→10），验收 3.0s
[22:25:35] 取消打断（验收期内出字，这一发成功）        ← 同一个原因再取消一次
[22:26:17] 打满后已有实质产出，本轮不续跑              ← 连耗尽续跑也被清掉
```

DOM 实测形态：`aside > div > div > span.wrap-anywhere`，文本 75 字符，`growthEpsilon=40`。同一条会话里 `aside` 只有一种用途（错误框组件），所以容器校验对它既便宜又准。

改法两条：

- `platform.highDemandText`（默认 `high\s+demand`）单独一类，命中且**在错误框容器里**才算报错文案，从 `threadLen` 扣掉。长度不再被它污染，已有的随机临界（`thresholds: [7,8,9]` + 跳号 + 验收窗）就照常动手，不需要新加判据。
- `highDemandImmediate`：它经常不经过「正在重新连接 n/10」就直接被打回、停在发送态，这时 4.5 那条「打满证据」等不到（要求亲眼见过 `n == max`）。于是照 4.3 的三条判据（本轮新撞一个框 + 之后没有实质产出 + 本轮真的跑过）立刻发一句「继续」，框的数量同样在长度扫描那一趟里顺手数，不额外遍历 DOM。

限流那条一票否决对它不适用：验收窗内冒出 high demand 不撤销打断，这正是用户要的行为。

### 4.7 0.15.1：0.15.0 上线后仍然不打断，现场抓到两处

热重载后同一现象照旧（`已产出内容，重试应已成功` / `取消打断（验收期内出字）`）。只读轮询真实重试 55 秒，抓到两个 0.15.0 没料到的事实：

1. **同一句报错不止一份。** 除了 `aside` 里的 `span.wrap-anywhere`，每个重试行下面还挂一份 `div.text-size-chat.whitespace-pre-wrap`，历史轮每留一份 —— 当时那一屏是 **3 份、各 75 字**。0.15.0 给 high demand 加了容器校验（怕误扣正文），结果只扣掉 aside 那份，另外 150 字照旧算产出。这就是脚本自己注释里写过的「同一段报错会出现两份」，只是实际份数比预想更多。改法：扣长度时三类报错文案一视同仁、都不看容器；**看容器的是「本轮撞到」那份证据**（它驱动自动发「继续」，属于要动手的动作面）。
2. **活动行里有每秒变长的计时标签。** `span.tabular-nums.text-tertiary` 的 `已处理 1分钟 3秒` → `已处理 1分钟 15秒`，还有 `你在 0秒 后停止了`。逐字对比 12 秒内变化的文本节点定位到的。它 +1 字就刷新一次 `lastGrowthAt`，`flowing()` 于是长期为真、验收窗被撤；更糟的是它会**累计**，攒够 `growthEpsilon(40)` 就触发 `producedSinceRetry`，把重试会话和 `turnExhausted` 证据一起清掉 —— 上面日志里那两行「已产出内容」和「打满后已有实质产出」是它和报错文案叠加的结果。改法：`platform.activityTimerText` 把这类状态标签也从长度里扣掉（只扣长度，不驱动任何动作）。

正则两头锚死、且要求「数字 + 时间单位」，实测 8 条真实形态全命中，`已处理完这三批数据，接下来…`、`Processed 10 files and skipped 2…`、`耗时很久，请重试` 这些都不误命中。为什么不用 `grew` 加最小增长量（比如 ≥2 字才算流动）：那治不了累计过 40 的那条路，而且会把慢速流式输出误判成卡住。

jsdom 场景因此加到 A–L：**H** 改成三份文案一起挂在验收窗内，**L** 全程没有报错文案、只让计时标签跳动一格 —— 这两个在 0.15.0 和 0.14.1 上都是 0 次打断，在 0.15.1 上都按 7~9 临界打断。



## 5. 自托管读秒

### 0.14.0：对话隔离与异步安全

- 每个真实对话 UUID 使用独立的 `codexRetryRescue.selfHost.thread.<uuid>` localStorage 键。只存布尔值，不存消息内容；旧版全局 `selfHost` 不迁移。
- 不再限定 `01a0` 前缀。优先核对侧栏与正文的 ID；侧栏仍为临时 `client-new-thread` 时，从正文 DOM 的 React fiber 祖先读取 `conversationId` 与 `clientThreadId` 映射，最多 32 层，不遍历整棵树。身份不明确或两侧不一致时不自动发送。
- 计时器绑定创建时的对话 ID 与代次。取消后即使旧回调已排队，也不能清除新计时器或向别的聊天发送。
- 发送互斥；每次等待后核对对话 ID、输入框对象、人工输入时间与总开关。销毁旧脚本后，其异步回调不可继续动作。脚本同步写入期间的 input 事件不算人工输入（0.14.1 用 `composerWriteDepth` 标记；`execCommand` 生成的事件也可能 `isTrusted=true`，不能只检查该属性）。
- 切换对话时先清理旧轮次证据和 DOM 缓存，再分析新对话；暂停或发送中也执行清理。返回对话恢复开关，但不恢复旧倒计时。
- 移除“发送后很快回到空闲就补发”的逻辑：快速正常结束不等于发送失败。

### 计时规则

架构简单就够：一个 `setTimeout` + 一组打断条件，到点等价于「点一次继续按钮」，复用同一条发送路径。

踩过的三个坑：

- **不要在每次交互时重掷随机数**。一开始写成「打字/点击 → 重新抽 30–300s」，用户看到的就是读秒从 200 跳到几十，像坏了。
- **滑动屏幕、点空白不是人工干预**。只有输入框有实际输入、切会话、开新 turn 才取消本轮读秒，等下一轮结束再排。
- **本轮没跑过就不要排。** 「创建新项目」之后按钮一直是发送态，而发送态每拍都会走到「回到发送态且未接管」那条路 —— 早期版本在这里无条件 arm，于是脚本会自己往一条从没发过言的空会话里发「继续」。现在 arm 之前先取 `sawRunningTurn`（在这一拍被清掉之前），只有本轮真的见过停止钮才排。至于切走会话时已经在跑的计时，由切换检测里的 `cancelSelfHost` 负责。

间隔分布刻意不是均匀：`selfHostDelaySkew` 对均匀随机值取幂，使概率密度随秒数单调下降，小间隔更密——避免形成可被识别的固定节奏。

## 6. 后台保活为什么必须在进程外

用户脚本跑在 Electron 渲染进程里。窗口一最小化，Chromium 会把 `setInterval` 乃至 Worker 定时器掐到分钟级甚至暂停，**这一层在页面内怎么改都推不动**。

所以分两层：

- 页面内：主线程 `setInterval` + 一个 Worker 时钟（**仅在页面 hidden 时**补拍，否则前台会双打）+ `visibilitychange` 回前台立刻补一拍；
- 页面外：`codex-retry-watchdog.mjs` 连 Codex++ 打开的 CDP 调试端口，用 `Runtime.evaluate` 从外部强制注入 `kick()`。外部注入不受渲染进程节流影响，窗口看不见也能推进。顺带开 `Emulation.setFocusEmulationEnabled` 减轻限流（只是缓解，不是保证）。

看门狗在 `127.0.0.1:57328/ping` 提供存活接口，脚本只探测、探不到就显示「看门狗✗」，**不会自作主张把它拉起来**；这个 `/ping` 同时充当单实例锁。

## 7. 性能：这两次卡死的教训

出过一次「Codex 和 Codex++ 管理器一起卡死」的故障，根因是每拍的 DOM 成本：

| 重活 | 现在的处理 |
|---|---|
| 每拍全量扫重试候选 + 全文长度 | **一拍只扫一次**，结果复用，带 500ms TTL |
| 每拍读全文判断限流 | 缓存 3s，且只看尾部若干 KB |
| 每拍扫错误框 | 缓存 2s |
| 长度计算里排除错误框（`errorTextLeaves`） | **故意不缓存**：错误行一到就得停止计入产出，缓存会让长度虚高、把刚记下的「打满」证据当成已产出而清掉（实测全量扫一次约 1ms） |
| 每拍 `readCurrentThreadId()`（会遍历 React fiber） | 主循环里**只许用轻量侧栏 id**；fiber 扫描只允许人工触发 |
| interval 与 Worker 同时触发 | Worker 仅在 hidden 时补拍 |
| 单拍抛异常连锁停摆 | 主循环 try/catch |

**绝对不要用 MutationObserver 驱动这个脚本。** 状态条自身在被观察的子树里：改它 → 触发观察器 → 又改它，而观察器回调是微任务，这个环永远不让出事件循环，渲染进程主线程直接饿死。主循环必须是定时器。

## 8. UI 为什么收成一条工具条

界面只是读数窗口，不该抢对话区的面积，也不该有第二种配色。三条约束：

- **一份样式表**。指示器、继续、接续、自托管原本是四个各写 `cssText` 的胶囊，同一段玻璃拟态复制了四遍，改一个数值要动四处。现在 `ensureStyle()` 往 `<head>` 注入一次样式，元素只挂 class。
- **明暗跟随应用底色，而不是 `prefers-color-scheme`**。Codex 的应用内主题可以和系统设置相反，所以从对话区往上找第一个不透明背景算亮度（Rec.709），结果写进 `host.dataset.theme`，颜色全走 CSS 变量。换主题只翻一个属性，重绘函数不参与。
- **状态色收敛成 5 种语义**。14 个状态原来发 14 个色值，同一种绿分给三个状态，读不出差别。现在颜色只回答「现在要不要你操心」：灰=待命/暂停、蓝=正在跑、黄=在等、绿=成了、红=出事，具体在做什么交给文案。

动作键和拖动手柄在同一个元素上，所以 `attachDrag` 必须排除 `e.target.closest("button")`，否则点「继续」会顺带把整条拖走。

## 9. 平台适配层为什么 fail-closed

所有「报错长什么样」的正则集中在 `CONFIG.platform`，编译时包一层 try/catch，写坏就退化成「永不匹配」。方向是故意的：**认不出来 = 不救**，比认错 = 乱点你的界面安全得多。新增匹配项时要保持这个方向。

## 10. 加判定逻辑之前的自检清单

1. 会不会在**历史残留**内容上触发？（transcript 里的旧重试行、旧错误框）
2. turn 边界对不对？（切会话、新开一轮、脚本自己刚动过手之后状态有没有复位）
3. 会不会覆盖**用户正在打的草稿**？
4. 这一拍要扫多少 DOM？能不能缓存？会不会进 React？
5. 最坏情况下它会点哪个按钮？多点几次会怎样？（熔断/`maxRounds`/`maxMigrations` 够不够）
6. 未知态是否被当成已知态处理了？（「排队」被当成「继续」就是曾经的事故）
